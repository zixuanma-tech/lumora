# 博物馆导览 Agent：架构、工作流程与开发进度

更新日期：2026-10-22。

本文依据《需求文档.txt》《开发交接.md》、当前代码和本次实际验证整理。旧文档中与当前代码不一致的描述，以本文注明的现状为准。

## 1. 这个 Agent 做什么

游客说出兴趣和可用时间，系统安排路线；首件按需生成，之后在当前讲解期间提前准备下一件。途中可以追问、跳过展品或改变需求，系统保留已有记录，只重排待看部分。结束后，系统把本次讲解和问答整理成《探索手记》。

整个过程可以概括为：**了解需求 → 安排路线 → 逐件讲解 → 随时调整 → 整理手记**。

### 页面怎样调用后台

| 接口 | 用途 |
| --- | --- |
| `POST /api/session` | 新建一次游览 |
| `POST /api/event` | 处理按钮操作，如开始讲解、跳过、重排和结束 |
| `POST /api/chat` | 处理游客输入的文字 |
| `GET /api/state` | 读取本次游览的最新记录 |
| `GET /health` | 检查服务是否能响应 |

游览请求处理后，后台返回“本次结果”和“最新游览记录”，页面据此更新。页面不能直接覆盖后台的游览记录。

## 3. 一次游览怎样运行

### 第一步：创建游览，整理需求

页面先创建游览编号，区分不同游客的记录。游客填写可用时间，再输入想法或选择页面推荐主题。

系统把需求整理成五类：

| 游客信息 | 例子 |
| --- | --- |
| 内容兴趣 | 想了解青铜器、古人的生活 |
| 讲解风格 | 生动、通俗、简洁 |
| 讲解角度 | 制作工艺、历史背景 |
| 剩余时间 | 45 分钟 |
| 其他需求 | 带孩子、需要休息、无障碍需求 |

文字交给模型理解；按钮名称和已填好的字段由程序直接处理。一次输入可以同时包含需求调整和当前展品的问题。

### 第二步：安排路线

规划前需要有内容兴趣、剩余时间、当前位置和出口位置。还需要真实的展品与展厅资料。

程序按以下顺序工作：

1. 把游客兴趣整理成可匹配的标签，例如时代、品类、工艺、题材。
2. 把当前内容兴趣转换成一串数字，即“兴趣向量”。
3. 排除已参观和未开放的展品，为其余展品打分。
4. 每个展厅先选出适合的展品，再计算走路、穿厅、停留和跨楼层的时间。
5. 在时间允许的范围内安排展厅和展品顺序，写入待看列表。

每件展品的分数由三部分组成：

| 分数 | 判断什么 | 最高分 |
| --- | --- | --- |
| 标签分 | 游客要求与展品标签是否匹配 | 50 |
| 文字含义分 | 游客兴趣与展品介绍的意思有多接近 | 30 |
| 重要度分 | 展品本身的重要程度 | 20 |

文字含义比较的双方是：**游客兴趣向量 ↔ 每件展品提前保存的向量**。后台计算两个向量的接近程度，再换算成分数；当前接近程度不高于 0.5 时，这部分得 0 分。

每件展品的向量，需要先把名称、年代、类别、主题和权威介绍等文字交给向量模型生成并保存。游客兴趣和展品资料必须使用同一个模型、相同版本和相同向量长度。目前已验证 `GLM-Embedding-3` 返回 2048 个数字。

展品数量由时间和筛选结果决定，已经取消“全程固定 5–8 件”的早期设定。路线主要给分数高的展品安排停留，也可以在顺路时补入重要展品。

### 第三步：按需开始，提前准备下一件讲解

首件讲解由游客点击“开始讲解”触发；之后系统提前准备待看列表中的第一件，正式开始时复用准备稿：

1. 程序按展品编号读取全部候选资料原文和来源，不再用模型选材。
2. 将当前展品全部候选交给模型，按游客兴趣、风格、角度和问题撰写讲解，并在同一次生成中自检事实依据与引用，分成可播放的句子或段落。
3. 程序检查 JSON、展品与材料引用、分句和会话状态；后台准备稿仅暂存在会话缓存，用户正式开始时重新核对目标、需求版本和剩余时间，再保存讲稿并移入已参观列表。

候选资料至少包含资料编号、原文和来源。`JsonGuideDataSource` 已能按展品编号读取 `data/relics.json` 的 `materials[]`。当前 60 件 demo 文物共有 59 份材料，每件 0–1 份，正文 23–198 字，因此独立模型选材收益很小；“全部候选”仅指当前展品，不是全馆资料。

默认讲解从三次串行模型请求减为一次。生成内自检不能达到独立审核的同等保障，不能仅靠来源 ID 或 JSON 合法证明事实正确；需要用真实资料检查忠实度并测量实际耗时。原独立选材和审核适配器保留，供自定义服务显式启用。

**只有正式开始并提交主讲才记为已参观，后台准备完成不记为已参观；正式记录也不表示游客已经听完。** 实际播放进度另外保存。整篇讲解完成并通过本地校验后才下发；缓存就绪时可直接取稿，仍在生成时等待同一请求。聊天追问还会先调用一次输入解析，再调用一次讲解生成。

当前只提前准备下一件，不自动播放。纯追问、暂停续播、刷新和自然倒计时保留缓存；偏好变化、显式重设时间、重规划、位置或出口变化、跳过使旧稿失效，结束或时间用尽则清空。旧模型请求即使晚返回也不会写入记录，连续变化只准备最新目标。后台等待不占用会话状态锁，不会让追问或播放进度排在后台生成后面。缓存只保存在当前服务进程，重启后丢失；首件和未准备好的下一件仍有生成等待。

### 第四步：追问、跳过和调整路线

| 游客操作 | 系统怎么处理 |
| --- | --- |
| 追问当前展品 | 根据当前展品、问题和播放进度生成独立回答，保存原问题与回答 |
| 回答后继续讲解 | 后台保留原稿和中断位置，支持请求恢复；真实音频播放仍待接入 |
| 改兴趣、时间或其他需求 | 更新游客信息，从当前位置重新安排待看部分 |
| 只改讲解风格或角度 | 留给后续讲解使用，通常不重排路线 |
| 跳过展品 | 移出待看列表，记为跳过，不计入已参观 |
| 更新位置 | 保存真实当前位置，供之后规划使用 |

重排不会删除已参观记录、原讲稿或问答。当前跳过的展品可能在之后重排时再次被推荐。

后台按实际经过的时间扣减余额；预计路线用时只是规划参考。时间用完会清空待看列表，但不会自动结束游览。新路线生成失败时保留旧列表，并提示路线需要更新。

### 第五步：结束游览，整理手记

游客可以填写最有印象的展品和感想，两项都能跳过。

系统结束游览，读取本次成功生成的全部主讲和问答，并查询相关展品的名称、年代和展厅。模型据此整理手记，再由另一次模型请求检查。

手记包括参观足迹、沿途发现、有依据的展品联系、精选问答和后续探索方向。个人感想按游客原意保留。

手记按已生成内容取材，不按是否听完筛选。结束后停止修改游览记录；手记失败时可以重新请求生成。

## 4. 模型具体做哪五件事

五项文本工作默认使用同一个 `GLM-5.3-Flash`，沿用 Paratera 接口与现有密钥；每项使用不同的要求和输入。

| 模型工作 | 输入 | 输出 |
| --- | --- | --- |
| 理解输入 `interpreter` | 游客文字、当前游客信息和讲解情况 | 需求变化、当前问题、重排或结束意图 |
| 整理兴趣 `interest_parser` | 当前游客信息 | 路线打分所需的兴趣标签 |
| 写讲解并自检 `composer` | 当前展品全部候选、游客需求、问题和播放上下文 | 最终主讲稿或追问回答 |
| 写手记 `summary_composer` | 参观记录、全部讲解问答、展品资料和反馈 | 探索手记草稿 |
| 检查手记 `summary_reviewer` | 本次记录和手记草稿 | 是否通过，以及具体问题 |

`selector` 注入字段现在默认装配本地材料加载器，不发送模型请求；默认 `reviewer=None`，`guide_review_mode="integrated"`。直接使用原算子或自定义 `RouterServices` 时默认仍为 `independent`，须显式提供审核服务；自检模式的结果为 `review=None`，不会伪造审核通过。

向量服务单独使用 `GLM-Embedding-3`，负责把文字变成数字，不属于上述五项工作。

模型负责理解和写作；程序负责打分、算路、计时、检查格式和保存记录。讲解和手记的模型检查还需要用真实资料验证效果。

## 6. 现在还要做什么

### 先补齐完整演示需要的内容

| 顺序 | 待完成任务 | 完成后能做什么 |
| --- | --- | --- |
| 1 | 准备真实展品资料、标签、重要度和权威来源 | 让推荐和讲解有真实内容可用 |
| 2 | 准备展厅、楼层、入口、出口、通路和步行时间，并接入路线读取功能 | 让系统按真实场馆安排路线 |
| 3 | 按统一文字格式为每件展品生成 2048 维向量，并保存模型信息 | 让游客兴趣与真实展品进行含义比较 |
| 4 | 复核已接入候选资料的权威性、完整性与事实范围 | 提高讲解依据质量，资料不足时明确说明 |
| 5 | 接入手记所需的展品名称、年代和展厅资料 | 让真实游览记录能生成完整手记 |
| 6 | 用真实密钥和资料验证五项模型工作，测量新模型的生成用时 | 确认理解、写作、自检、手记审核和返回格式符合要求 |
| 7 | 把讲解文字变成声音，接入真实音频播放、暂停、追问和恢复 | 让播放进度代表实际听到的位置 |
| 8 | 从手机页面完整走一遍需求、路线、讲解、调整和手记 | 找出页面与后台配合的问题，校准路线时间和讲解效果 |

`data/relics.json` 和 `data/edges.json` 已填充 60 件国博 demo 文物和 45 条知识关联。展厅通路单独来自 `data/map.json`，当前是功能测试用的虚拟地图，不能用展品知识关系代替，也不能视为真实馆内通路。

本轮最初使用 `DeepSeek-V4.1-Flash-1017` 时，服务商返回 HTTP 403（`team_model_access_denied`）；按用户要求改为 `DeepSeek-V4.1-Flash` 后仍返回 HTTP 403，未成功生成。相同接口与密钥调用旧 GLM-5.3 可成功。随后按用户要求改用 `GLM-5.3-Flash`，真实 `demo-pot` 主讲单次 `guide_draft` 请求成功，耗时 23.31 秒，返回 252 字、6 个播放单元，并以 `integrated` 模式、`review=None` 保存。该结果仅是一个样本，不能代表稳定速度或讲解质量，尚未全面语义核验。

补充当前馆藏链路实测：`NMC-CQ-104` 主讲单次请求 28.59 秒，返回 164 字、4 个播放单元；资料不足追问单次请求 13.65 秒，返回 110 字、3 个播放单元，并明确提示资料不足。两次均仅发送一次 `guide_draft`；主讲和回答共保存两条记录，已参观展品仍为一件，原稿续播上下文保留。以上与演示主讲的 23.31 秒均为各一次样本，不是稳定均值，也未完成全面语义质量验证。本轮默认模型更新后全量 218 项测试再次通过。

本轮下一件预生成真实验证：沿用 `GLM-5.3-Flash`，A=`NMC-CQ-104` 生成 32.42 秒，B=`NMC-CQ-105` 后台生成 36.20 秒；准备 B 时只有 A 被正式记录。B 就绪后点击开始，后端取稿约 0.0008 秒，总模型请求 2 次，最终 2 条正式记录。该单次样本不代表稳定均值，取稿时间不含网络、浏览器和语音启动。
