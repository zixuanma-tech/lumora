## 讲解生成联网（2026-10-22）

讲解生成已具备联网能力。本轮针对“明确资料不足仍不搜索”调整提示词：旧版末尾附加允许联网，但正文与自检反复要求全部事实仅来自候选材料、超范围直接说明不足，形成冲突。当前按开关选择完整、一致的本地或联网证据策略，仍不强制每次请求都搜索：

- `model_api.py`：`LLMConfig` 新增 `guide_web_search: bool = False`（非布尔即拒绝）；`ChatCompletionsClient.__call__` 新增 `web_search` 关键字参数，为 True 时请求载荷附加 `tools: [{"type":"web_search","web_search":{"enable":true,"search_result":true}}]`（GLM 服务端内置工具，搜索由模型侧执行，响应仍是普通 content，`finish_reason=stop`）。
- `guide_prompts.py`：公共讲解模板保留主讲/追问、播放边界、JSON 与自检约束；`GUIDE_COMPOSER_SYSTEM_PROMPT` 采用仅本地材料策略，`GUIDE_COMPOSER_WEB_SYSTEM_PROMPT` 采用联网策略。`build_guide_composer_messages`、`make_guide_composer` 新增可选布尔参数 `web_search_enabled=False`，不依赖厂商 SDK。联网时先把问题或指定讲解角度拆成事实清单，只有候选材料对事实有直接陈述才算覆盖；同主题、关键词相似、一般背景或材料稀疏泛化均视为缺口。缺口、时效信息或明确查询核实要求均须先检索，再撰稿；检索后仍无可靠依据才说明无法确认。模型记忆不能补证，网页指令也只作数据。用展品名称、来源线索与问题词查询，核对同件身份与来源可靠性；已明确的本地事实优先，可靠网络资料可补充缺失事实与背景，但不能把一般背景套成本件具体用途或经历。
- `model_services.py`：`load_llm_config` 支持 `LUMORA_LLM_GUIDE_WEB_SEARCH=true/false` 环境变量覆盖；`build_model_services` 在 `guide_web_search=true` 且走默认装配时，选择完整联网证据策略，wrapper 只传 `web_search=True`。已删除旧 `GUIDE_WEB_SEARCH_USER_HINT`、`GUIDE_WEB_SEARCH_ADDENDUM`。联网 user 消息前置自然语言的条件检索要求，并将本次问题明确标为数据，再附 `GUIDE_COMPOSER_WEB_DATA_MARKER` 与完整任务 JSON；关闭联网仍直接传 JSON。实测只把任务放进 JSON 不易触发，直接前置同一检索任务才触发了实际搜索。其余四项职责与注入的 `model_call` 不受影响。
- 引用与范围：`used_material_ids` 继续非空且只记录正文实际使用的本地候选材料；不代表网络证据，不能填写网址或自造 ID，也不能用本地 ID 冒充网络结论依据。正文自然结合材料确认的展品特征或资料范围；使用网络资料时说明“根据公开网络资料”，不输出网址清单。默认 `integrated` 自检使用相同证据策略；显式注入的旧独立 reviewer 仍只认本地材料，不应直接拿它审核联网扩展事实。
- `config/llm_config.json` 与示例：新增 `"guide_web_search": true`；`timeout` 120→240（联网讲解实测 39–92 秒，120 秒曾真实超时一次）。

## 实用测试：下一件讲解预生成（2026-10-22）

已实现并默认开启。A 正式生成并提交后，Router 在后台准备待看队首 B；每会话只缓存下一件，不自动播放。`build_guide_request()` 构造不可变请求，`prepare_guide()` 返回不可变 `PreparedGuide`，不接触可变会话、不分配稿件 ID，也不写 `guide_records`、`visited_relics` 或消费队列。用户点击 `start_guide` 时，Router 重新核对会话、目标、历史、偏好、版本和实际时间，再用同步 `commit_prepared_guide()` 一次提交；已就绪直接复用，生成中等待同一任务，重复点击不会重复调用或记录。

纯追问只追加问答日志，不影响下一件缓存；播放进度、暂停续播、刷新和自然时间流逝也保留。实际游客偏好变化、显式提交时间预算（即使数值相同）、明确重规划（即使队首相同）、位置或出口变化、跳过均增加讲解版本并清除有效缓存；结束或时间用尽也清空。讲解 prompt 禁止播报具体剩余分钟数，避免缓存内容随倒计时过时。

2026-10-22 修复“下一件已备好，点击仍加载并可能超时”：开始讲解前及生成结束后都会检查实时预算，旧实现一旦自动重规划，就重新调用兴趣解析模型并无条件清除预生成稿，即使队首仍为同一展品。现在仅对自然倒计时触发的自动重规划，复用上次成功规划的馆藏快照、结构化兴趣和查询向量，在本地按剩余预算重新计算；队首与讲解所需历史、偏好未变时保留 ready/inflight 任务，队首改变、重规划失败或时间用尽仍作废。规划缓存仅在会话内保存，不下发浏览器；显式重规划仍重新加载数据和调用规划依赖。汝窑天青釉盘（`NMC-CQ-107`）本地材料加载正常，此缺陷由时间预算边界触发，无展品专属分支。

`_Session.prefetch` 保存有效准备任务及结果，`background_job` 追踪真实未结束的后台请求，`foreground_job` 供正式开始请求共享；缓存只在进程内会话中保存，不写磁盘，重启会丢失。失效采用版本号和事件，等待中的开始请求可及时返回，不必等旧 HTTP 完成；已发出的 urllib HTTP 不强制取消，旧结果丢弃，连续变动只在旧后台请求结束后安排最新目标。后台准备及主讲等待不持会话锁；任务完成回调另行短暂加锁调度下一项，避免模型等待阻塞追问或段落进度。

`Router(..., prefetch_enabled=True, prefetch_concurrency=2)` 为默认值，全局后台配额为 2，正式请求与追问不受该配额排队；未发送的排队预生成在点击时可提升为前台。后台失败保留 `failed` 状态、不自行重试，用户正式开始时再试。`reply_content.guide_prefetch` 只含 `status=idle/generating/ready/failed` 与 `relic_id`，不返回预生成正文。页面仅更新待看队首的准备提示，沿用现有状态响应和播放进度回报，不新增轮询、忙碌遮罩或自动播放。自定义调用方关闭服务时须 `await router.aclose()`，HTTP 服务的 `server_close()` 已接入。

原 `op_generate_guide()` 入口复用准备/提交流程，继续在每次外部 await 后检查完整会话快照；Router 的后台主讲使用不可变请求，并在正式消费时核对版本，允许自然时间和纯问答变化。QA 继续走原算子入口。状态更新、输入、规划及问答操作仍按会话持锁；锁外主讲准备不修改状态。

## 项目与当前进度

项目是博物馆导览 Agent，采用“规划 → 按需讲解 → 动态重规划”。每次游览拥有独立的 `SessionState`，后续由 Router 按 `session_id` 管理。

已实现 `session_state.py`、第一个算子 `op_process_input()`、语音讲解上下文 `GuideContext`、第二个算子 `op_plan_route()`，以及第三个算子 `op_generate_guide()`、第四个算子 `op_generate_summary()` 的可注入执行流程。路线规划分为 `route_models.py`（数据契约和参数）、`route_scoring.py`（六维评分和展厅聚合）、`route_graph.py`（有向最短通路）、`route_planner.py`（搜索、裁剪、召回和状态提交）。讲解分为 `guide_models.py`（不可变数据契约及语音上下文）、`guide_generator.py`（资料加载、表达、校验和提交）；手记分为 `summary_models.py`（不可变数据契约）、`summary_data.py`（按 ID 读取基础资料）、`summary_generator.py`（组装输入、表达、校验和核对），入口均由 `operators.py` 导出。中央路由 `router.py` 已实现为可注入、内存态调度层；`model_services.py` 已统一装配五项模型职责及本地材料加载器，配置指向 `https://llmapi.paratera.com` 的 `GLM-5.3-Flash`。`main.py` 已提供 HTTP 入口，默认通过 `demo_museum.build_demo_services()` 装配真实模型职责与独立的虚构演示场馆。`index.html`、`style.css`、`app.js` 提供寻迹暖色 H5、自然表达及游览时间入口、主题选择、无需填写即可浏览的推荐路线、路线讲解/跳过/追问/重规划、位置选择、结束反馈及手记重试。前端从 `reply_content.playback.current` 恢复原稿与进度，使用浏览器 SpeechSynthesis 朗读，仅在 `onend` 后回报完整段落，不再使用定时器模拟完成。真实馆藏、语义向量库、商用 TTS 和持久化仍待接入。

## 游客信息：只保留五类

使用名称“游客信息”，对应不可变数据类 `VisitorInfo`。这是用户确认后的最新划分，替代早期需求文档中较笼统的“游客偏好”。

| 字段名 | 含义 | 内部类型 / 默认值 |
| --- | --- | --- |
| `content_interests` | 内容兴趣：想看或了解什么，也包含学习目标、问题或主题 | `tuple[str, ...]` / `()` |
| `guide_styles` | 讲解风格：生动、通俗、简洁、深入等 | `tuple[str, ...]` / `()` |
| `guide_focus` | 讲解角度：制作工艺、历史背景、与课本的联系等 | `tuple[str, ...]` / `()` |
| `remaining_minutes` | 剩余时间，单位为分钟；初始填写本次可用时间 | `float \| None` / `None`，也接受整数 |
| `other_needs` | 其他需求或信息：年龄、亲子同行、无障碍、休息等 | `tuple[str, ...]` / `()` |

五类都可缺省；时间 `None` 表示未知，`0` 表示已用尽。文字列表允许完整描述、跨字段重叠，目前不限制词表；同一字段内去重并保留顺序。例如“想了解制作工艺”可以同时体现在内容兴趣和讲解角度中。

游客信息只保存提炼后的当前有效信息，不保存偏好调整的原话历史、输入来源或推断标记。不再设置独立的游览目标、主题路线 ID、同行人员或年龄字段。解析算子负责理解输入，状态类只校验和保存。追问的问题与成功生成的回答另外保存在讲解记录中，不属于游客信息。

```python
state.update_visitor_info(
    content_interests=["想了解古人如何制作青铜器"],
    guide_styles=["生动", "通俗"],
    guide_focus=["材料选择", "制作过程"],
    remaining_minutes=45,
    other_needs=["家长带 8 岁孩子同行"],
)
```

## SessionState 接口与约束

导入 `SessionState`、`VisitorInfo`、`RouteStop`、`VisitRecord`、`GuideRecord`；构造方式为 `SessionState(visitor_info=None, *, session_id=None)`，未提供 ID 时自动生成 UUID。

| 属性 | 内容 |
| --- | --- |
| `session_id` | 会话 ID，字符串 |
| `visitor_info` | 当前 `VisitorInfo` |
| `visited_relics` | 按顺序保存的 `tuple[VisitRecord, ...]` |
| `visited_relic_ids` | 从已参观记录派生的 ID 元组 |
| `guide_records` | 按生成成功顺序保存的 `tuple[GuideRecord, ...]`，包含完整主讲及追问问答 |
| `pending_queue` | 按顺序保存的 `tuple[RouteStop, ...]` |
| `skipped_relics` | 跳过的展品 ID 元组，不算已参观 |
| `current_relic_id` | 最近完成讲解生成的展品 ID；没有则为 `None`，语音尚未播完时追问须优先使用 `GuideContext` |
| `status` | `"active"` 或 `"finished"` |

`RouteStop` 字段：`relic_id`、`recommendation_reason`、`connection_from_previous`，后两项默认为空字符串。
`VisitRecord` 具有上述三个字段，以及必填的 `guide_text`，保存讲解完成时的快照。
`GuideRecord` 字段为 `guide_id`、`relic_id`、`kind`（`"guide"` / `"answer"`）、`segments`、可选 `question`。`segments` 保留原文分句，`guide_text` 属性拼接得到正文。回答必须附带问题，主讲不能附带问题。记录不可变且只追加，生成成功不等于实际听过。

- `update_visitor_info(**changes)`：局部更新并返回 `VisitorInfo`；未传字段保留，传入列表替换该字段，`[]` 清空列表，时间传 `None` 清空。
- `replace_pending_queue(stops)`：替换待参观队列；元素可为 `RouteStop`、展品 ID 字符串或对应字段字典。禁止重复展品、已参观展品。
- `record_guide(record)`：统一保存一条 `GuideRecord`。主讲必须匹配队首，一次校验成功后同时追加讲解记录、追加 `VisitRecord` 和移除队首，返回该参观记录；追问回答仅追加讲解记录并返回 `None`，不改主讲原稿、参观轨迹或待看队列。追问目标须为最近完成的展品或正在讲解的队首。重复稿件 ID、结束会话或校验失败时不修改状态。依据核对仍由第三算子负责。
- `complete_visit(relic_id, guide_text)`：保留旧签名的兼容入口，为单单元主讲稿生成新 ID，内部调用 `record_guide()`。第三算子直接调用 `record_guide()`，保留与 `GuideContext` 一致的真实稿件 ID 和分句。
- `get_guide_record(guide_id)`：按稿件 ID 读取服务端原文；找不到时抛出 `KeyError`。可用于中断恢复及后续手记取材。
- `skip_next(*, expected_relic_id=None)`：移除队首、记录跳过，返回 `RouteStop`；建议传预期 ID 防止操作过期路线。跳过项是否再次推荐由规划算子决定。
- `finish()`：结束游览，可重复调用；保留轨迹、讲解记录和未完成队列，结束后拒绝修改游客信息、路线或讲解记录。
- `to_dict()`：返回独立、可 JSON 序列化的快照，元组变为列表；顶层键为上述属性中的 `session_id`、`visitor_info`、`visited_relics`、`guide_records`、`pending_queue`、`skipped_relics`、`current_relic_id`、`status`，不含 `visited_relic_ids`。讲解正文可从记录的 `segments` 拼接获得，不额外序列化一份派生正文。
- `SessionState.from_dict(data)`：从服务端保存的可信快照恢复并校验；必须有原会话 ID，不接收客户端快照来覆盖服务端状态。含讲解日志的新快照要求稿件 ID 唯一、主讲顺序及正文与参观轨迹一致。旧快照缺少 `guide_records` 时，按已有 `VisitRecord` 补建主讲日志并分配新 ID；旧版未保存的问答、原稿 ID 和真实分句无法恢复，不补造。

公开状态通过方法更新。已参观轨迹与讲解记录只能追加，跳过和重规划均不删除已生成问答；校验失败不提交更新。旧版“总路线 5–8 件”已取消，展品数量由单厅 Top-K 和时间预算决定。时间扣减、史料查询、知识边审核由调用方及后续算子处理。同一会话的可变状态操作须由 Router 持锁协调，纯讲稿准备可在锁外进行。当前数据仍由内存对象持有，支持快照序列化，但尚无自动落盘或数据库。

## 中央路由（已实现）

`router.py` 提供 `Router`、`RouterServices` 以及两个薄封装 `dispatch_action(router, session_id, action, payload=None)`、`dispatch_chat(router, session_id, text, playback=None)`。路由器按 `session_id` 保存独立会话，用每会话 `asyncio.Lock` 协调状态修改和提交；主讲准备与后台预生成在锁外等待，不同会话可以并发。`create_session()` 只创建会话，不自动规划，调用方需提供真实当前位置和出口节点后再触发 `replan`。

按钮事件包括 `submit_preferences`、`update_visitor_info`、`replan`、`start_guide`、`skip`、`update_location`、`playback_progress`、`resume_guide`、`finish`、`generate_summary`、`get_state`。结构化游客信息始终交给 `op_process_input()` 校验；自然语言由 `dispatch_chat()` 交给同一算子。混合输入按“提交游客信息 → 生成当前展品追问回答 → 必要时重规划”执行。路线重规划仅使用 Router 保存的 `current_node_id`，不从最近生成讲解推断位置；内容兴趣、剩余时间、其他需求变化或明确重规划会使路线标记为 `route_dirty`，仅讲解风格和角度变化留给后续讲解。

Router 独立保存最近一次完整规划结果、最近一次规划尝试及播放状态。`no_feasible_route` 或规划异常时保留 `SessionState.pending_queue`，并保持 `route_dirty=True`，拒绝继续使用失效路线开始讲解。`time_exhausted` 只清空待看队列，不结束游览。剩余时间按单调时钟在请求进入和结束时扣减；显式提交 `remaining_minutes` 会在提交后重置计时基准，结束会话后冻结余额。规划返回的预计 `time_bill.remaining_min` 不会直接扣除真实余额。

播放状态以服务端 `GuideRecord` 原文为准。客户端只能回报 `guide_id` 和已完整播放的连续单元数，旧稿、倒退或越界进度会被拒绝。追问前保存当前主讲 `GuideContext` 到续播栈，回答生成独立稿件；回答播放完成后 `resume_guide` 按栈顺序恢复原稿和其已确认进度。`finish` 幂等；结束后若注入手记服务，Router 自动调用第四算子并返回 `summary`，失败时保留已结束状态并允许后续 `generate_summary` 重试。

每次响应形如 `{reply_content, latest_state}`；`latest_state` 始终来自服务端 `state.to_dict()`。`reply_content` 至少含 `status`、`message`、`route`、`plan_result`、`route_dirty`、当前位置、播放状态和 `summary`；自然语言回答或主讲成功时附带 `guide=result.to_dict()`。`generate_summary` 只允许结束后的会话调用，反馈可通过 `favorite_relic_id` 和 `reflection` 传入。当前路由状态为进程内存，尚无自动落盘、多进程锁或鉴权；HTTP 入口由 `main.py` 提供。

按钮事件仍直接路由；问卷、游客信息调整和聊天由输入算子处理。自然语言可以同时包含整体需求和当前展品追问，不再强制从互斥的 `REPLAN` / `QA_CURRENT` / `FINISH` 三选一。已提供 `POST /api/event`、`POST /api/chat`，统一返回 `{ reply_content, latest_state }`，其中 `latest_state = state.to_dict()`。展品史料和关联边分别来自 `data/relics.json`、`data/edges.json`；2026-10-21 起两者已由队友的国博数据包 Excel 转换填充（60 件 demo 文物、45 条知识关联），同批生成 `data/galleries.json`（4 展厅底座）与 `data/routes.json`（8 条推荐路线），转换口径见 `scripts/build_demo_data.py` 文档串。

## 第一个算子：统一输入处理

```python
result = await op_process_input(
    state, user_input, interpreter=interpreter, guide_context=guide_context,
)
```

- `user_input` 为五类游客信息的字段字典时，直接校验并局部更新，不调用分析器。字段语义与 `update_visitor_info()` 相同。
- `user_input` 为非空字符串时，调用注入的异步 `InputInterpreter`。未提供分析器时抛出 `NotImplementedError`，暂不使用关键词规则替代模型理解。
- 分析器调用形式为 `await interpreter(text, visitor_info=..., current_visit=..., guide_context=...)`。上下文均不可变，不向分析器暴露可修改的会话对象；正在讲的展品尚无已完成记录时，`current_visit` 为 `None`，不能把上一件的讲解当作当前讲解。
- 分析器必须返回 `InputAnalysis(visitor_info_changes={}, question=None, replan_requested=False, finish_requested=False)`。涉及的游客信息字段须给出完整新值；未涉及字段不输出。当前展品问题放入 `question`，不自动写入游客信息。明确的重规划和结束意图分别置相应标志。
- 全部分析结果和游客信息校验成功后才提交更新；失败不提交。算子不修改参观轨迹、讲解日志、待看队列或结束状态；不承担讲稿及问答的存储职责。
- 返回 `InputResult`：更新后的 `visitor_info`、实际变化的 `changed_fields`、`question`、问题对应的 `current_relic_id`、原样传递的 `guide_context`，以及明确的重规划/结束意图标志。这里的问题目标 ID 优先采用讲解上下文中的展品，与状态类派生的最近完成展品可能不同。`replan_requested` 仅表示明确要求重规划；Router 还需根据 `changed_fields` 判断信息变化是否需要调整路线。
- 追问由 Router 立即交给后续讲解算子，输入算子不直接调用其他算子。混合输入先更新游客信息，再使用新信息回答当前问题，之后安排需要的后续规划。
- 有问题但既无讲解上下文、也无已完成讲解的展品时，`result.needs_current_relic` 为 `True`。保留问题供 Router 明确当前展品；仅有待看队首不能证明用户正在听它，也不把问题改存为兴趣。
- 同一会话调用仍须由 Router 串行处理。`input_interpreter_prompt.py` 已提供模型无关的 `INPUT_INTERPRETER_SYSTEM_PROMPT`、`INPUT_INTERPRETER_JSON_SCHEMA`、`build_input_interpreter_messages()` 和 `parse_input_analysis()`；`model_services.make_input_interpreter()` 将其装配为 `InputInterpreter`，模型 JSON 输出仍交给原解析函数返回 `InputAnalysis`。Prompt 不绑定具体 SDK，不回答追问，也不提交会话状态；`op_process_input()` 继续负责最终字段校验和更新。

### 第二个算子：兴趣解析提示词

`interest_prompts.py` 已提供可直接交给模型 SDK 的 `INTEREST_PARSER_SYSTEM_PROMPT`、`INTEREST_PROFILE_JSON_SCHEMA`、`build_interest_parser_messages()`、`parse_interest_profile()` 和 `make_interest_parser()`。它把不可变的 `VisitorInfo` 转换为路线规划使用的 `InterestProfile`，不读取数据库、不选择展品、不计算分数，也不修改游客信息。

输出字段与 `route_models.InterestProfile` 一致：`target_eras`、`target_regions`、`target_categories`、`target_craft_types` 为字符串数组，内部表示 OR；`target_themes`、`target_aesthetics`、`target_cultural_ip`、`target_audience` 为字符串数组的数组，内层表示 OR、外层表示独立目标；`query_text` 用于后续向量检索。`guide_styles` 和 `remaining_minutes` 不进入兴趣标签；`other_needs` 只有明确表达受众或体验适配时才进入 `target_audience`。

应用可以向 `build_interest_parser_messages()`、`make_interest_parser()` 或 `build_model_services()` 传入可选的 `taxonomy`，格式为 `eras`、`regions`、`categories`、`craft_types`、`themes`、`aesthetics`、`cultural_ip`、`audience` 到规范词列表的映射。提供词汇表后，模型只能从对应维度的规范词中选择；未提供时保留用户明确表达的短语。模型调用层由应用启动层注入，返回值交给 `parse_interest_profile()` 后再传入 `op_plan_route()`。

自定义模型调用时，适配器的核心流程如下；现成服务装配见文末“统一模型 API 接入”：

```python
from input_interpreter_prompt import (
    INPUT_INTERPRETER_JSON_SCHEMA,
    build_input_interpreter_messages,
    parse_input_analysis,
)

async def interpreter(text, *, visitor_info, current_visit, guide_context):
    messages = build_input_interpreter_messages(
        text, visitor_info=visitor_info, current_visit=current_visit,
        guide_context=guide_context,
    )
    raw_json = await model_call(
        messages, response_schema=INPUT_INTERPRETER_JSON_SCHEMA,
    )
    return parse_input_analysis(raw_json)
```

## 语音追问的讲解上下文

用户已确定使用语音讲解，进度按实际播放到的句子或段落记录。为第一版统一按完整播放单元计数，建议使用句子；打断在句中时，该句仍算未播完，恢复时可从句首重播。

`GuideContext` 在 `guide_models.py` 定义，仍可从 `operators.py` 导入。成功生成的分句原文和稿件 ID 已保存在 `SessionState.guide_records`；播放进度及当前稿件版本由后续 Router 按会话维护并提供：

| 字段 / 属性 | 含义 |
| --- | --- |
| `session_id` | 所属会话 ID，防止串会话 |
| `relic_id` | 正在播放或被中断的展品 ID |
| `guide_id` | 一版稿件的唯一 ID；改稿须换新 ID |
| `segments` | 服务端保存的稿件播放单元元组 |
| `completed_segments` | 前端确认完整播完的连续前缀长度，范围为 0 到 `len(segments)` |
| `generation_complete` | 全文是否生成完；流式生成未完成时，`segments` 只是当前已生成稿件 |
| `played_segments` | 由播放进度派生的已播完部分 |
| `remaining_segments` | 由播放进度派生的待续部分，包含可能只播了一半的句子 |

- 不把模型已生成、已下发音频或已加入播放队列当作用户已听完。
- Router 应在追问时暂停播放，取得实际播放进度，并核对回报的 `guide_id` 与服务端当前稿件版本；旧稿件的迟到回报不能覆盖新稿件进度。稿件原文由服务端读取，不能由客户端提交后覆盖。
- 对完整稿件，Router 可用 `state.get_guide_record(guide_id)` 取得原文分句，再结合该稿件已确认的播放进度构建 `GuideContext`。生成尚未完成的临时分句仍需由 Router 另行持有；当前第三算子只返回完整生成结果。仅凭日志不能恢复播放位置。
- 输入算子检查上下文类型、会话归属和展品是否是队首或最近完成的展品；使用中的稿件 ID、回报的新旧和进度更新由 Router 负责。
- 讲解算子接收问题、游客信息和此上下文，供适配器区分已播与待播内容；初代生成独立回答并原样返回 `resume_context`，由 Router 安排回答播放及恢复原稿。暂不自动改写未播部分。Prompt 已由 `guide_prompts.py` 提供，模型调用已纳入统一服务装配；实际播放器的暂停与续播仍待接入。
- `VisitRecord` 和 `GuideRecord` 均是已完成生成的快照，不能据此推断语音已经播放完。主讲仍在完整生成且通过本地校验后才提交参观；independent 模式另需独立核对，播放状态与已参观轨迹分开处理。

### 数据源与模型接入

算子是异步函数，直接接收已解析标签、向量和数据快照，也可注入三个异步适配器。当前未接入图数据库；默认服务通过 `backend/catalog_data.py` 读取国博 demo 数据，并使用 `data/map.json` 的虚拟空间快照测试规划。`data/edges.json` 继续表示知识关联边，与空间边分开；真实馆内拓扑和步行时间仍待实地核验。

- `MuseumDataSource.load() -> MuseumSnapshot`：提供一次规划的一致性馆藏/空间快照。
- `InterestParser(*, visitor_info: VisitorInfo) -> InterestProfile`：从当前游客信息中生成结构化六维兴趣。接收不可变游客信息，不持有会话对象；`build_model_services()` 已装配模型解析器，也允许显式提供 `interests`。
- `VectorService.embed_query(text: str) -> Sequence[float]`：文本为 `content_interests` 用分号连接的当前内容兴趣。馆藏向量由数据源提供，应由同一编码模型、版本和维数预先生成；缺失、零向量、维数不一致或非有限值会报错，保留原待看队列。

快照可以用数据类实例或对应字段字典构建：

| 数据类 | 主要字段 |
| --- | --- |
| `MuseumSnapshot` | `galleries`、`exhibits`、`edges`、`node_floors`；前三者为序列 |
| `Gallery` | `gallery_id`、`name`、`node_id`（默认等于厅 ID）、`floor`、`base_pass_min`、`entry_coords`（默认 `(0,0)`） |
| `Exhibit` | `exhibit_id`、`name`、`gallery_id`、`tags`、`vector`、`importance_level`（1–5）、`is_open`、`coords`、`dwell_time_map`、`crowd_factor` |
| `SpatialEdge` | `source`、`target`、`walk_time_min`；有方向，不自动添加反向边 |

`node_floors` 保存入口、出口、楼梯、连廊等所有普通空间节点的楼层；展厅节点自动由 `galleries` 加入。空间边的端点必须存在，楼层必须一致。所有时间单位均为分钟。空间边的步行时间不能预先包含展厅固定穿行时间，否则会重复计费。展厅关闭时，数据源应移除其停留候选并提供真实可通行拓扑；单品关闭直接设 `is_open=False`。

### 六维标签字段与打分

| 六维含义 | 文物 `ExhibitTags` 字段 | 兴趣 `InterestProfile` 字段 |
| --- | --- | --- |
| 时空与文化圈 | `era_broad`、`era_specific`、`regions` | `target_eras`、`target_regions` |
| 器物与工艺材质 | `category_main`、`craft_types` | `target_categories`、`target_craft_types` |
| 题材与生活场景 | `themes` | `target_themes` |
| 视觉与审美特征 | `aesthetics` | `target_aesthetics` |
| 文化 IP 与知名度 | `cultural_ip` | `target_cultural_ip` |
| 受众与体验适配 | `audience` | `target_audience` |

标签必须由上游解析器归一化为馆藏所用词汇；本地不通过关键词猜测用户意图。时代、地域、一级品类、工艺目标各自为 OR；后四维中普通字符串是独立目标，内层序列是一组 OR 备选。未提及维度不进入分母。

已确认的新公式为 `S_tag = min(50, 50 * Σ(w_d*M_d)/Σ(w_d) * beta)`，权重依次为 `25/25/20/10/10/10`。前两维对用户指定的子部分取平均；层级大类匹配已知子类为 1，只有父类信息时为 0.5，明确的不同子类为 0。内置层级仅覆盖常见朝代及示例工艺，可通过配置扩展。后四维命中数除以 `min(目标数,2)` 并上限截断为 1，OR 组仅贡献一次命中。时代与一级品类均完全匹配时 `beta=1.3`，仅其中一项完全匹配时 `0.7`，其余 `1.0`。

语义分保持余弦相似度阈值 0.5 后线性拉伸至 0–30；价值分为 `20*importance_level/5`。三项相加默认范围 0–100。过滤已参观或关闭文物后才验证和评分，因此这些过滤项不需要可用向量。跳过项按当前规则可以再次推荐；知识串联字段暂留空，不能伪造知识关联。

### 搜索与时间账单

1. 每厅保留综合分至少 60 的展品，按分数降序、ID 决胜，取单厅 Top-K；收益按 `0.85**rank` 衰减，停留时间含 `base_pass_min + Σ(dwell*crowd)`。
2. 有向 Dijkstra 将中间展厅的固定穿行时间纳入选路；相同通行耗时优先较少跨层和较少边数。起终点的厅基础时间由整条路线计入，避免与核心停留双计；同一厅再次作为路过节点时照常计穿行。
3. 不超过 12 个候选厅时使用子集动态规划。状态为 `(已选厅集合,末厅,已用免费跨层次数)`，保留最短名义耗时。固定集合的 Top-K 和低分尾部剔除次序相同，因此更短路径不会降低裁剪后的核心收益。**精确最优限于已预计算的最短通路、单厅 Top-K 和指定的尾部剔除规则，不是任意展品子集、任意空间通路的联合全局最优。**
4. 超过 12 厅采用按新增收益/新增时间插入的贪心，结合展厅时间性价比排序，再做 2-opt；反转后重新验证全部有向路径。该分支不保证全局最优。
5. 净预算为剩余时间的 90%。名义路线超时不超过 15 分钟时，逐次删除所有停留厅中分数最低的末位展品，重算收益；目前不压缩驻足时间。被删空的厅仍保留为空间途经点和基础穿行时间。
6. 第三次及其后的每次楼层变化增加 3 分钟规划罚时。所有空间边上的楼层变化都计数，不只比较核心厅楼层。“不走回头路”不作严格空间节点约束；同一核心厅只停留一次，路线允许再次穿过该厅。
7. 核心路线确定后，在纯途经厅插入未看、开放、重要度为 5 的文物，每件快速打卡 4 分钟，按分数和 ID 排序选择，确保总时间不超过剩余时间。不会为补偿绕路，不向已停留核心厅额外塞入国宝。
8. 各厅展品按从 `entry_coords` 开始的最近邻排序，按实际路径出现位置展开至待看队列。厅内步行由固定穿行和驻足模型近似，尚无坐标距离到分钟的额外换算。

系数集中在 `PlannerConfig`，展品驻足时间默认 `quick=3 / standard=5 / deep=8`，拥挤系数默认 1；单厅 Top-K 默认 `3/5/8`。单品驻足时间由数据源设置，实验时也可通过 `dataclasses.replace()` 创建新的快照或参数，不必修改搜索代码。

返回 JSON 可序列化字典，主要字段：`status`、`search_method`、`optimality_scope`、`interest_profile`、`path_nodes`、`nodes`、`walk_legs`、`galleries`、`exhibits`、`core_gallery_ids`、`core_gain`、`dropped_highlights`、`time_bill`、`pending_queue_updated`。每件文物附三项评分、维度匹配度、推荐标签和驻足时间。`time_bill.total_min` 等于步行、厅穿行、核心驻足、国宝驻足和跨层罚时之和；保留的缓冲池不是自动额外消耗的时间。

完整结果由 Router 按会话另存；`SessionState` 仍只存展品级队列。算子计算和校验全部成功后，才一次替换 `pending_queue`，不改历史参观记录，不扣减 `remaining_minutes`。时间未知时要求补充；时间为零时清空队列并返回 `time_exhausted`，不表示用户已经到达出口。没有可行通路或净预算不足以通行时返回 `no_feasible_route`、`pending_queue_updated=False`，保留原队列，调用方应依据结果状态处理，不能把旧队列误当成新路线。没有核心展品但能通行时返回纯通行路线（仍可召回顺路国宝）。

## 第三个算子：讲解执行流程（已实现，Prompt 与模型调用已装配，知识库待接入）

用户确定初代只向讲解流程输入“参观过哪些文物”，暂不输入全部历史讲稿或大纲，不建立类比记忆或专门的重复检测。成功生成的主讲及追问问答全文统一保存到 `SessionState.guide_records`，供第四算子取材；全文保存不表示每次向第三算子传入全部全文。重复讲解问题留到整个 demo 完成后实际测试，再决定是否补充这些机制。

```python
from operators import op_generate_guide

result = await op_generate_guide(
    state,
    relic_id=state.pending_queue[0].relic_id,  # 建议携带按钮对应 ID，防止过期操作
    selector=selector,
    composer=composer,
    review_mode="integrated",               # 不传独立 reviewer
)
# result.guide_text 为完整稿，result.guide_context.segments 为待播放单元。
# result.guide_record 已追加到 state.guide_records，稿件 ID 与上下文一致。
# result.to_dict() 可 JSON 序列化；最新会话另取 state.to_dict()。
```

### 输入与一次模型生成

默认统一装配先本地加载当前展品全部候选，再调用一次模型组织表达并自检。`selector` 与 `composer` 必需；`integrated` 模式不接受独立 `reviewer`。自定义 `independent` 模式仍要求三项适配器，并在生成后调用独立审核；缺少必需服务抛出 `NotImplementedError`，不修改状态。两种模式都不提供规则讲稿或模型内部知识回退。

| 接口 | 输入 | 输出 |
| --- | --- | --- |
| `GuideSelector`（默认本地加载器） | `request=GuideRequest` | 当前展品全部候选组成的 `GuideSelection` |
| `GuideComposer` | `request=GuideRequest, selection=GuideSelection` | `GuideDraft` |
| `GuideReviewer`（仅 independent 模式） | `request=GuideRequest, selection=GuideSelection, draft=GuideDraft` | `GuideReview` |

`GuideRequest` 含 `session_id`、目标 `relic_id`、当前 `visitor_info`、按实际参观顺序排列的 `visited_relic_ids`、可选 `question`、`guide_context` 和 `current_guide_text`。同一份不可变请求传给三个阶段；不向适配器暴露可变状态。`visited_relic_ids` 直接取服务端状态，不含跳过或待看文物，也不表示对应语音已经播放完。

`request.connection_candidates` 为排除当前文物后倒序排列的历史 ID，建议先在已参观文物中查找有依据的关联，最近参观的在前；它只是关联候选，不能证明存在历史关系，也不强制每次串联。适配器可通过这些 ID 查询对应馆藏资料。历史讲稿、大纲及路线推荐理由均不作为史料输入。`current_guide_text` 仅在无语音上下文的当前展品追问时提供当前稿件，帮助理解指代；不推断游客已听完。

### 不绑定知识库的数据契约

上述数据类均在 `guide_models.py`，序列复制成元组：

- `GuideMaterial(material_id, text, source_refs, related_relic_ids=())`：候选知识段落，来源引用可为稳定来源 ID、文献页码或 URL；至少有一个引用。关联对象可选，不限定当前两个 JSON 的最终结构。
- `GuideSelection(relic_id, materials)`：当前文物的非空材料包，材料 ID 不重复。
- `GuideDraft(relic_id, segments, used_material_ids)`：完整草稿，按句或完整播放单元切分；实际使用的材料 ID 必须非空且全部来自材料包。内部不按标点猜分句。
- `GuideReview(approved, issues=())`：独立核对结果；有待解决问题不能标记通过。独立审核的 Prompt 和闭包保留给 `independent` 模式；默认统一装配不调用，不以“存在来源 ID”宣称事实正确。
- `GuideResult`：保存请求、材料包、草稿、可选核对结果、`review_mode`、新的 `guide_context`、已写入会话的 `guide_record`、可选 `resume_context` 与本次追加的 `visit_record`，并提供 `guide_text` 和 `to_dict()`。`integrated` 模式的 `review=None`，不代表独立审核通过。

本地只校验类型、目标、来源非空和引用范围，不能证明材料权威或草稿忠实于来源；默认由生成 Prompt 要求同次自检，效果仍需实际复核。需要独立依据核对时显式使用 `independent` 模式及 `GuideReviewer`。`guide_prompts.py` 提供模型无关的系统提示、严格 JSON Schema、上下文消息、解析器及异步调用闭包，测试使用合成材料和模拟服务。

### 追问与状态提交

- 没有 `question` 时视为首次讲解，只允许当前队首；建议总是传 `relic_id` 防止旧按钮操作到新的队首。已有语音上下文不作为首次生成参数，原稿续播由 Router 处理。
- 有 `question` 时优先使用 `guide_context.relic_id`，其次使用最近完成生成的 `state.current_relic_id`；不能仅凭待看队首确定当前展品。显式 ID 与目标不一致时拒绝。无上下文且无已完成稿件时要求先明确展品。
- 完整生成并通过本地校验后，主讲与问答均调用 `record_guide()` 保存；independent 模式另需独立核对。仅主讲同时提交参观、移除队首；追问只追加完整问题与回答，不覆盖主讲或已有问答。异常、无材料、无出处、错展品、未知材料引用或独立核对拒绝均不写入讲解日志、不提交参观。
- 新稿件使用新 `guide_id`，同一个 ID 与原始分句同时用于 `GuideRecord` 和 `GuideContext`；返回的 `generation_complete=True`、`completed_segments=0`。追问回答拥有自己的新上下文，同时原样返回传入的 `resume_context` 供恢复原稿；Router 可从共享状态按 ID 读取主讲与回答，分别管理当前播放版本和进度，不能用回答覆盖中断的主讲上下文。
- 初代等待完整稿件核对成功后再返回分句结果，未实现实时 token 流、TTS、播放上报、自动改稿或自动续播。
- 直接调用 `op_generate_guide()` 时仍要求同一会话串行处理；每次外部 `await` 后比较完整会话快照，变化时终止本次流程，不回滚其他请求已经提交的变化。Router 的主讲准备使用不可变请求，锁外等待、正式消费时核对版本；纯追问及自然倒计时不使下一件缓存失效。算子不扣减剩余时间。

### 讲解验证

`test_guide_operator.py` 与 `test_session_history.py` 覆盖历史 ID 在三个阶段的传递及顺序、跳过与待看项排除、关联候选顺序、首次生成成功提交、完整问答日志保存及快照恢复、追问不修改轨迹与原稿、原上下文续播信息保留、依赖缺失、错误输出及核对拒绝的失败原子性，以及任一异步阶段会话变化后的过期结果拒绝。测试使用模拟服务验证执行契约，不代表真实讲解效果或事实准确率已经通过验证。

## 第四个算子：探索手记（已实现，Prompt 与模型调用已装配，真实数据源待接入）

首版从本次完整讲解与问答中整理可收藏的结构化《探索手记》。展品基础资料按 ID 查询 `data`；不需要传入 `GuideResult`，不新增长期收藏、笔记或个人感想功能。用户已确定直接采用已生成的完整讲解作为取材，不以播放完成度筛选；`visited_relics` 作为参观足迹，无须额外确认是否听完。

结束时两个问题均可跳过，文案由 `summary_models.SUMMARY_QUESTIONS` 提供：

1. 这次哪件展品最让你有印象？
2. 这次游览有什么感想？

答案使用 `SummaryFeedback(favorite_relic_id=None, reflection=None)`。印象展品必须来自本次已参观列表；感想保留原文、换行和首尾空格，纯空白视为未回答。它们仅作为此次生成参数及结果中的反馈，不修改五类游客信息，也不写入 `SessionState`。

```python
from operators import op_generate_summary
from summary_models import SummaryFeedback

# 可在 state.finish() 后调用；此算子本身不结束游览，也不修改会话。
result = await op_generate_summary(
    state,
    feedback=SummaryFeedback(
        favorite_relic_id="relic-001",  # 可不传
        reflection="原来这些纹饰还有这样的含义。",  # 可不传
    ),
    composer=composer,
    reviewer=reviewer,
    # data_source=...，未传则读取项目 data/relics.json
)
reply_content = result.to_dict()
```

### 输入与资料查询

`SummaryRequest` 包含 `session_id`、当前 `visitor_info`、按参观顺序排列的 `visited_relics`、全程 `guide_records`、查询得到的 `relics`、`feedback`。这些数据均不可变，同一请求传给表达和核对阶段，服务不持有可修改的会话。

- 主讲与问答全文均读取 `SessionState`，保留所有成功稿件的生成顺序、稿件 ID、原问题和分句；不另外传 `GuideResult`，也不从模型内部知识补讲解。
- `visited_relics` 决定参观足迹，待看和跳过展品不混入。队首主讲完成前也可能产生问答，因此这类已保存的问答仍参与取材、查询其基础资料，但不会增加参观足迹。
- 需要查询的 ID 先按参观顺序排列，再追加仅出现在讲解日志中的展品并去重。资料可乱序返回，算子恢复请求顺序；缺失、重复、额外 ID 或无名称会显式失败。
- `SummaryDataSource.load_relics(relic_ids: tuple[str, ...])` 为异步适配器，返回 `SummaryRelic` 序列。`SummaryRelic` 字段为 `relic_id`、`name`、可选 `era` 和 `gallery_name`。
- 默认 `JsonSummaryDataSource` 读取 `data/relics.json`，最小结构为 `{"relics": [{"relic_id": "...", "name": "...", "era": "...", "gallery_name": "..."}]}`；后两个字段可省略，其他字段忽略。当前文件已由 `scripts/build_demo_data.py` 从队友的国博数据 Excel 生成，条目还携带六标签 `tags`（era_broad/era_specific/category_main/craft_types/artifact_types/motifs/themes）、`materials`（GuideMaterial 形状的讲解史料，含 related_relic_ids）、`importance_level`（5=镇馆之宝，4=核心，3=候选；镇馆标注为测试用近似口径）等扩展字段。
- 不推算实际游览时间，不将推荐理由或规划过渡语当作新增史料。首版知识联系来自本次讲解已有内容，不额外查询 `edges.json` 扩写新知识。

### 生成接口与输出

异步 `SummaryComposer(request=...) -> SummaryDraft` 负责整理表达，`SummaryReviewer(request=..., draft=...) -> SummaryReview` 核对是否忠实于讲解、问答和用户反馈。二者均须注入，可直接由 `build_model_services()` 装配；`summary_prompts.py` 提供模型无关的系统提示、严格 JSON Schema、上下文消息、解析器及异步调用闭包，不提供默认批准或规则替代讲稿。

`SummaryDraft` 字段：

| 字段 | 含义与契约 |
| --- | --- |
| `title`、`introduction` | 非空标题与简短开篇 |
| `trail` | `SummaryStop(relic_id, recap)` 序列，严格保留全部已参观展品及其顺序 |
| `discoveries` | 至少一项 `SummaryInsight(title, text, relic_ids, guide_ids)`，内容多少按实际游览调整，不硬凑数量 |
| `connections` | 可选的 `SummaryInsight` 序列，每项至少关联两件展品 |
| `questions` | 可选 `SummaryQuestion(guide_id, answer_summary)` 序列，只能引用真实问答稿件且不能重复；原问题直接从日志取，不允许模型改写 |
| `next_exploration` | 可选的下次探索方向 |

每项发现及联系必须有展品 ID 和稿件 ID，二者的展品集合须对应；本地验证引用范围，不宣称仅凭 ID 就能证明语义正确。是否忠于原讲解、是否把个人感想误写成史实等由注入的 `SummaryReviewer` 模型服务独立检查，提示与适配闭包已由 `summary_prompts.py` 提供。`SummaryReview(approved, issues=())` 存在问题时不可批准，拒绝或错误输出不返回成功手记。

`SummaryResult` 含内部请求、草稿和核对结果，`status` 为 `generated` 或 `empty`。`to_dict()` 返回独立且可 JSON 序列化的展示结构：`status`、`session_id`、`title`、`introduction`、`relics`（含问答涉及展品的基础资料表）、`trail`（附名称、年代及展厅）、`discoveries`、`connections`、`questions`（附原问题、展品 ID 与名称）、`next_exploration`、原始 `feedback`。不重复输出全程讲稿或内部核对数据；前端可基于该结构呈现页面或后续分享卡，当前不生成图片/PDF、不实现前端页面。

### 状态边界与验证

- 支持 `active` 和 `finished` 会话；不调用 `finish()`，不更改路线、游客信息、讲解日志或参观记录。生成结果由调用方按会话另存，当前不增加自动落盘。
- 既没有参观也没有问答记录时直接返回 `empty`，不需要或调用资料/模型服务；仅有队首问答时也可生成，参观足迹为空。
- 每次外部 `await` 后比较会话快照，变化时拒绝过期结果；不回滚其他请求已经提交的更新。生成异常、资料缺失、引用不合法、核对拒绝均不修改会话。
- `test_summary_operator.py` 和 `test_summary_data.py` 覆盖完整主讲与问答取材、反馈可缺省及感想原文、结束后重复生成、空结果、队首问答、资料查询、错误引用、缺少依赖、异常与核对拒绝、各异步阶段会话变化；`test_guide_prompts.py`、`test_summary_prompts.py` 和 `test_prompt_boundaries.py` 覆盖 Prompt Schema、上下文消息、严格 JSON 解析、代码围栏与模型包装、重复 JSON 字段、缺字段、错误类型、ID 范围与引用匹配、空内容、Reviewer 结果约束、异步候选/模型注入，以及五个适配器接入原算子的成功与拒绝路径。当前在 `D:\lumora\agent_v0` 目录运行 `& 'D:\tools\anaconda\python.exe' -B -m unittest discover -s .`，全量 **199 项通过**，只验证本地执行契约，未验证真实模型生成质量。



## Prompt 适配层（新增）

第三个算子的适配位于 `guide_prompts.py`。默认通过 `make_guide_material_loader(candidates)` 本地加载全部候选，通过 `make_guide_composer(model_call)` 在一次请求内撰稿与自检；分别适配 `GuideSelector(request) -> GuideSelection`、`GuideComposer(request, selection) -> GuideDraft`。本地草稿解析核对 relic_id、非空播放单元和材料引用。`GUIDE_SELECTOR_SYSTEM_PROMPT`、`GUIDE_REVIEWER_SYSTEM_PROMPT` 及 `make_guide_selector` / `make_guide_reviewer` 保留给自定义独立选材、审核；默认链路不调用。模型调用仍注入异步 `model_call(**{system_prompt, user_prompt, response_format})`。

第四个算子的模型适配位于 `summary_prompts.py`。该模块提供 `SUMMARY_COMPOSER_SYSTEM_PROMPT`、`SUMMARY_REVIEWER_SYSTEM_PROMPT` 及对应 Schema、`build_summary_composer_messages()`、`build_summary_reviewer_messages()`、`parse_summary_draft()`、`parse_summary_review()` 和两个异步注入闭包。Composer 输入完整不可变 `SummaryRequest`，输出 `SummaryDraft`；本地解析强制 trail 覆盖已参观展品且顺序一致、discoveries 非空、跨展品联系至少两件展品、展品/讲解 ID 与请求匹配、精选问答只引用真实 answer 记录。Reviewer 独立接收 request 和 draft，只有 `approved=true` 且 issues 为空才可通过数据类约束。

上述 Prompt 模块只传递 JSON 数据，不依赖具体模型厂商 SDK、固定数据库表结构或真实数据库；实际服务由应用启动层注入，可使用现成的 `build_model_services()`。所有模型输出先经过 JSON 解析、现有数据类构造及算子 `_validate_draft` 等本地校验。模型 HTTP 调用已接入并以实际配置验证；当前演示馆、浏览器播放器及项目 HTTP 入口已接通。真实馆藏、商用 TTS 仍未接入，最新验证见前端与演示启动章节。

### 模型服务注入与 JSON 格式

`model_call` 必须是异步可调用对象，接收 `system_prompt`、`user_prompt` 和 `response_format` 三个关键字参数，返回 JSON 字符串或已解码对象。Prompt 层内部仍携带名称、严格标记和 JSON Schema；统一 HTTP 客户端会把它转换为配置的 `response_format={"type":"json_object"}`，并把 Schema 追加到系统指令。适配闭包只解析返回值，不加载 SDK、不管理 API 密钥、不重试或默认批准；新 Flash 模型的真实格式兼容性尚待成功联调确认。

```python
from guide_prompts import make_guide_material_loader, make_guide_composer
from summary_prompts import make_summary_composer, make_summary_reviewer

# candidates 是应用按当前目标注入的非空 GuideMaterial 序列。
selector = make_guide_material_loader(candidates)  # 本地加载全部候选
composer = make_guide_composer(composer_model_call)
summary_composer = make_summary_composer(summary_composer_model_call)
summary_reviewer = make_summary_reviewer(summary_reviewer_model_call)

# 讲解传 selector、composer、review_mode="integrated"，不传 reviewer。
# 手记仍传 composer=summary_composer、reviewer=summary_reviewer。
```

多展品共用一套 Router 服务时，`candidates` 也接受异步 `async def load_candidates(*, request)`：按 `request.relic_id` 从自有资料层返回当前展品的完整 `GuideMaterial` 序列，再传给 `make_guide_material_loader(load_candidates)`。固定序列会在创建闭包时复制；异步资料源每次请求加载并校验，所有材料原样进入生成输入，不再让模型回抄材料。候选的目标归属由注入层保证，`GuideMaterial` 没有额外的展品归属字段；`related_relic_ids` 表示查证后的关联对象，不能用来推断当前目标或创建关系。

解析只接受结果对象或完整 JSON 字符串；允许完整的无语言/`json` 代码围栏，但围栏内仍执行相同字段、类型和引用校验。未知/缺失字段、重复 JSON 键、非法 JSON 常量、SDK 包装或前后说明均拒绝，部署层需先提取 SDK 的 JSON 正文。播放单元保留原文、空格和重复内容；材料及稿件引用不能静默去重以绕过数据类约束。默认讲解在生成请求内自检，不输出或构造独立审核结论；手记及显式启用的讲解 independent 模式仍独立调用 Reviewer。Reviewer 的 `approved=true` 时 issues 必须为空，`approved=false` 时本 Prompt 解析要求至少一个具体问题。来源权威性、事实忠实度、问题回应、反馈归属和语言适配需要实际质量复核，单元测试不代表真实模型质量已验证。

默认讲解材料包由程序原样构造，无 Selector 模型输出。Composer 输出 `{"relic_id":"r1","segments":["适合播放的一个单元。"],"used_material_ids":["m1"]}`，引用范围在本地和既有算子再次检查。显式使用模型 Selector 时，其输出仍为 `{"relic_id":"r1","materials":[{"material_id":"m1","text":"材料原文","source_refs":["来源 ID"],"related_relic_ids":[]}]}`，本地逐项核对全文与来源；显式独立 Reviewer 输出 `{"approved":true,"issues":[]}` 或 `{"approved":false,"issues":["具体、可修复的问题"]}`。

手记 Composer 输出 `SummaryDraft` 对应的全部七个顶层键：`title`、`introduction`、`trail`、`discoveries`、`connections`、`questions`、`next_exploration`。`trail` 为 `{"relic_id":"r1","recap":"回顾"}` 数组；发现和联系为 `{"title":"标题","text":"内容","relic_ids":["r1"],"guide_ids":["g1"]}` 数组，联系至少两件展品；问答为 `{"guide_id":"真实 answer ID","answer_summary":"摘要"}` 数组。原问题从日志补回，禁止模型输出额外问题字段；`next_exploration` 为非空字符串或 `null`。手记 Reviewer 使用相同的 `approved` / `issues` 结构。

## 统一模型 API 接入（2026-10-20 实现，2026-10-22 更新默认装配）

用户追加要求把现有模型职责接到截图中的服务，密钥先使用占位值。`model_api.py` 实现标准库异步 Chat Completions HTTP 传输、正文提取、应用配置 `LLMConfig`、可配置路径和可选 Embeddings 适配；`model_services.py` 读取配置并一次装配 `RouterServices`。Prompt 模块及四个算子的调用方式保持不变，不增加模型 SDK 依赖。

`llm_config.json` 当前非敏感配置为：`base_url="https://llmapi.paratera.com"`、`model="GLM-5.3-Flash"`、`chat_path="/chat/completions"`、`timeout=120`、`response_mode="json_object"`；`embedding_model="GLM-Embedding-3"`、`embeddings_path="/embeddings"`。示例密钥为 `REPLACE_WITH_YOUR_API_KEY`，真实密钥通过环境变量读取。没有自动添加 `/v1`；若部署服务的实际路径不同，修改相应配置。`json_object` 沿用旧服务配置，已由 `GLM-5.3-Flash` 单次真实讲解请求验证可完成 JSON 解析与保存；其余职责与全面语义质量仍需验证。

`load_llm_config(path=None, *, environ=None)` 默认读取项目根目录下的 `config/llm_config.json`，该本地文件不存在时读取 `config/llm_config.example.json`，启动工作目录不影响查找。每个字段均可由 `LUMORA_LLM_<大写字段名>` 环境变量覆盖，例如 `LUMORA_LLM_BASE_URL`、`LUMORA_LLM_MODEL`、`LUMORA_LLM_CHAT_PATH`、`LUMORA_LLM_RESPONSE_MODE` 和 `LUMORA_LLM_TIMEOUT`；未知字段、重复 JSON 字段和非有限数值会被拒绝。真实密钥建议在启动环境中设置：

```powershell
$env:LUMORA_LLM_API_KEY = "真实密钥"
```

`build_model_services()` 返回可直接传给 `Router` 的 `RouterServices`，默认模型职责为以下五项：

| RouterServices 字段 | 模型职责 |
| --- | --- |
| `interpreter` | 自然语言输入解析，复用原输入 Prompt |
| `interest_parser` | 路线兴趣解析，复用原兴趣 Prompt |
| `composer` | 在一次生成中组织主讲或当前追问回答并自检 |
| `summary_composer` | 整理探索手记 |
| `summary_reviewer` | 独立核对手记草稿 |

五项共用同一文本模型配置；只有手记 Reviewer 默认独立发送模型请求。`selector` 字段装配本地全候选加载器，`reviewer=None`，`guide_review_mode="integrated"`。原独立模型适配器仍可显式注入自定义 `RouterServices`；服务装配本身不发送网络请求。

```python
from model_services import build_model_services
from router import Router

# 以下对象来自应用自己的真实资料层。
services = build_model_services(
    candidates=load_candidates,          # async def load_candidates(*, request)
    snapshot=museum_snapshot,            # 或 data_source=...，二者择一
    vector_service=vector_service,
    summary_data_source=summary_source,
)
router = Router(services)
```

`candidates` 也可传固定 `GuideMaterial` 序列；多展品由 `JsonGuideDataSource` 按 `request.relic_id` 读取 `data/relics.json` 的 `materials[]`。没有官方介绍的展品会在材料加载阶段明确报错，不会用模型知识补造史料。默认规划通过 `JsonMuseumDataSource` 读取 `data/galleries.json`、`data/relics.json` 和独立的 `data/map.json`；手记资料源仍单独注入，不会改动数据库结构。

测试或自定义服务可传 `model_call=...`，继续满足既有 Prompt 调用契约；也可传 `transport=...`，拦截实际 HTTP 请求并返回模拟 Chat Completions 响应。可运行 `./set_lumora_api_key.ps1` 隐藏输入密钥；加 `-PersistUser` 保存到当前用户环境变量，默认只设置当前 PowerShell 会话；密钥不会写入项目配置。自定义模型调用与底层 transport 二者择一，配置对象和配置路径也二者择一；注入 `model_call` 后不能同时传配置对象或配置路径，配置由该调用对象自行管理。

HTTP 客户端按当前服务商约束发送 `response_format={"type":"json_object"}`，并把内部 Schema 加入系统指令；所有输出仍必须通过原有本地 JSON、数据类和算子校验，服务端格式约束不替代本地校验。兼容模式只能显式配置，不会在服务失败后自动降级、重试或更换地址。认证、超时、连接、无效正文和未完整输出以固定错误描述返回，不向调用方回显服务错误体或密钥。

截图未提供 Embeddings 配置；当前已根据用户确认配置 `GLM-Embedding-3`。规划的 `VectorService` 可继续独立注入；明确配置 `embedding_model` 后统一装配会使用同一客户端调用 `embeddings_path`。必须使用与馆藏预生成向量相同的编码模型、版本和维数，不能把文本模型自动当作向量模型。空向量、零向量、非有限数值或无效响应会被拒绝，维数匹配仍由规划算子检查。
